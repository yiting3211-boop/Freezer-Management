# 冷凍倉儲管理系統技術方案（MVP）

## 建議方案

採用前後端分離的模組化單體：前端使用 **Vue 3、TypeScript、Vite**；後端使用 **NestJS（Node.js／TypeScript）**；資料庫使用 **PostgreSQL**，以 **Prisma** 管理資料模型與資料庫遷移。透過 REST API 連接前後端，使用 Docker Compose 部署應用程式與資料庫。

這套組合能以一套 TypeScript 技術串接前後端，適合小團隊快速交付單倉 MVP；模組化單體也比一開始拆分微服務更容易維護與部署。

## 需求與技術對應

- **批次、效期、商品與儲位查詢：** PostgreSQL 關聯式資料模型，明確保存商品、批次、儲位及庫存。
- **出入庫、盤點、報廢：** NestJS 業務模組與資料庫交易；以庫存異動帳記錄單據、數量變化、原因、操作人及時間。盤點差異和報廢在確認後才過帳。
- **防止超量出庫：** 在同一資料庫交易中鎖定並檢查批次可用庫存，再執行扣帳，避免並行操作造成超出庫存。
- **FEFO、臨期查詢與批次追溯：** 依效期排序提供揀貨建議，並由批次關聯查詢入庫、異動、盤點、報廢及出庫紀錄。
- **角色與基本資料：** MVP 提供管理員、主管、作業人員等簡易角色權限，並維護商品、合作夥伴及儲位。
- **報表與資料交接：** 後端提供庫存、臨期、盤點差異與報廢查詢，CSV 匯入／匯出由前端操作、後端驗證。
- **溫度異常：** 先支援人工登記及 CSV 匯入；感測器、即時告警與外部系統整合留待後續階段。

## 建議模組

前端按總覽、庫存、入庫、出庫、盤點／報廢、報表及基本資料拆分頁面。後端依序建立身分與權限、主檔、庫存、作業單據、追溯及報表模組；初期部署為單一 API 服務，不引入微服務或訊息佇列。

## 交付次序

1. 建立資料庫模型、登入與角色權限，以及商品、批次、倉庫／儲位主檔。
2. 完成入庫上架、庫存查詢、庫存異動帳及 FEFO 出庫。
3. 完成盤點差異確認、報廢確認與批次追溯。
4. 加入臨期／溫度異常查詢、基礎報表及 CSV 匯入／匯出。
5. 依現場確認的單位換算、效期規則、盤點期間作業方式和報廢權責調整流程。

## 驗收重點

- 每筆庫存異動皆能追溯至單據、批次、原因、操作人與時間。
- 出庫只扣除可用庫存，且依效期提供 FEFO 揀貨建議。
- 盤點差異及報廢須有原因並經確認後才更新庫存。
- 可從批次查到來源、儲位、歷次異動及出庫去向。
- 主管可查詢臨期、盤點差異、報廢與溫度異常資料。

## 現有原型

目前目錄中的 `app.js`、`index.html` 與 `styles.css` 是瀏覽器端示範原型，庫存資料存在記憶體中，重新載入即還原，也沒有登入、資料庫或多使用者並行保護。它適合流程討論與介面驗證；正式 MVP 應依上述方案補上 API、持久化資料及權限控制。
